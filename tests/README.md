# Проверка обновления схемы ClickHouse

Тест `test_clickhouse_upgrade.py` проверяет записи `market.book_agg`, которые
формируют реальные сборщики: без синхронизации (`resync`) и с живым стаканом
(`ok`), для каждой поддерживаемой биржи.

Он проверяет два пути:

1. Новая пустая база → SQL из проверяемой версии → вставка строк сборщиков.
2. База из старой Git-ревизии с данными → SQL из проверяемой версии → старые
   строки сохранились → новые строки вставляются.

SQL проверяемой версии выполняется дважды, чтобы проверить повторный деплой.
Тест проверяет наличие всех отправляемых столбцов, вставляет строки в формате
`JSONEachRow`, как рабочий сборщик, и сравнивает прочитанные значения с исходными.
Это важно: ClickHouse 25.8 по умолчанию использует
`input_format_skip_unknown_fields=1` и может молча отбросить неизвестное поле.
Одной проверки успешного INSERT недостаточно. Отсутствующий столбец, ошибка
вставки или потерянное значение завершают тест с ненулевым кодом.

Каждый запуск создаёт отдельный временный контейнер ClickHouse и удаляет его
вместе с данными при завершении, включая завершение с ошибкой. Контейнер не
публикует порты и работает без сети. Рабочая база и секреты не используются.

## Локальный запуск

Нужны Python 3.10+, Git и работающий Docker, доступный текущему пользователю.
При первом запуске Docker скачает официальный образ ClickHouse 25.8,
закреплённый по digest. Для другой версии можно передать `--image`.

Из корня репозитория:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
git fetch origin main
python tests/test_clickhouse_upgrade.py --base-ref origin/main
```

По умолчанию проверяется текущая рабочая директория, включая несохранённые в
коммит изменения SQL и кода. `--base-ref` задаёт старую версию схемы; она должна
быть доступна в локальной Git-истории. Для проверки обновления уже развёрнутой
версии передайте её commit SHA вместо `origin/main`.

Тест не входит в набор быстрых юнит-тестов: Docker нужен только для его запуска.

## Проверить существующий PR без переключения своей ветки

Например, проверить PR #3 относительно версии до интеграции Bybit:

```bash
git fetch origin pull/3/head:refs/remotes/origin/schema-test-pr
python tests/test_clickhouse_upgrade.py \
  --base-ref 2d657ec3e3505ffbb8971c1ea1aa6678393d54cc \
  --target-ref refs/remotes/origin/schema-test-pr
```

Тестовый код остаётся в текущей ветке, а код сборщиков и SQL берутся из указанной
Git-ревизии. Незакоммиченные изменения в ней не учитываются.

На версии PR #3 `acad0fe095dfd20ab447f3f304729dbb8ef0e1ad` создание новой базы
проходит, а обновление старой падает с
`Collector fields missing from market.book_agg: book_age_s`.
Причина: новый код отправляет это поле, но повторный `CREATE TABLE IF NOT EXISTS`
не добавляет его в уже существующую таблицу.

При стандартной настройке ClickHouse 25.8 запись остальных полей продолжилась
бы, но `book_age_s` терялся бы. При `input_format_skip_unknown_fields=0` сервер
отклонил бы пакет целиком. Тест выявляет отсутствие столбца в обоих случаях.

### Увидеть успешную проверку с предлагаемой миграцией

Чтобы сначала проверить исправление без изменений ветки PR, создайте отдельный
SQL-файл и примените его только в тестовом контейнере:

```bash
migration_sql="$(mktemp)"
cat > "$migration_sql" <<'SQL'
ALTER TABLE market.book_agg
ADD COLUMN IF NOT EXISTS book_age_s UInt32
CODEC(Delta(4), ZSTD(3)) AFTER n_updates;
SQL
python tests/test_clickhouse_upgrade.py \
  --base-ref 2d657ec3e3505ffbb8971c1ea1aa6678393d54cc \
  --target-ref refs/remotes/origin/schema-test-pr \
  --extra-sql "$migration_sql"
rm "$migration_sql"
```

Оба сценария должны пройти. Это демонстрация исправления, а не миграция рабочей
базы. Для самого исправления такой SQL нужно добавить в PR отдельным файлом
`schema/006_book_age.sql`. Обычный деплой применит его до перезапуска сборщиков.
Затем нужно проверить обновлённую ветку ещё раз уже **без** `--extra-sql`.

Этот тест не проверяет корректность рыночных расчётов и не гарантирует, что
полностью проверены миграции других таблиц или все исторические значения.

## GitHub Actions

Workflow **ClickHouse schema upgrade** запускается при открытии и обновлении PR,
при push в ветку и вручную. Проверка не требует секретов и использует обычный
`pull_request`, поэтому работает и для PR из публичных форков. GitHub может
попросить владельца разрешить запуск через **Approve workflows**.

Ветка с workflow проверяется уже после push, до слияния. После слияния workflow в `main`
появляется возможность вручную проверить любой существующий PR:

1. Откройте **Actions → ClickHouse schema upgrade → Run workflow**.
2. Выберите ветку `main`, в `pr_number` укажите `3`.
3. В `baseline_ref` укажите `2d657ec3e3505ffbb8971c1ea1aa6678393d54cc`, чтобы
   каждый раз проверять обновление одной и той же старой версии.
4. Запустите workflow. В шаге **Test fresh schema and upgrade** будет видна
   ошибка отсутствующего столбца `book_age_s`; в начале лога записан точный SHA
   проверяемого PR.
5. После добавления миграции и push в ветку PR выполните **Run workflow** снова
   с теми же параметрами. Ожидаются два сообщения `PASS`.

Ручной запуск виден во вкладке Actions; он не прикрепляет результат как проверку
к PR #3. Чтобы в самом PR появился автоматический check, его ветка должна
получить этот workflow: после слияния теста в `main` обновите PR через **Update
branch**, если кнопка доступна, либо автор должен влить актуальный `main` в свою
ветку и сделать push. Новый push запустит workflow для PR. Простое повторение
старого запуска не добавляет отсутствующий workflow в старую ветку.

Для автоматического запрета слияния при ошибке добавьте check **schema-upgrade**
в обязательные проверки защиты `main`. Само наличие workflow слияние не блокирует.
