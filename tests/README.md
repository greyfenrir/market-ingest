# Проверка обновления схемы ClickHouse

`test_clickhouse_upgrade.py` проверяет строки `market.book_agg` от реальных
сборщиков Binance и Bybit на искусственных сообщениях биржи. Для каждой биржи
создаются строки `resync` и `ok`; живые строки содержат ненулевой `book_age_s`.

Для Binance снимок покрывает только ближайший уровень с каждой стороны.
Обновление добавляет уровни за его пределами: обычная и накопленная глубины
различаются во всех четырёх диапазонах. Объёмы дробные, поэтому тест различает
округление до долларов и простое отбрасывание дробной части.

Проверяются новая база и обновление базы из старой Git-ревизии. В сценарии
обновления после подготовительного этапа пишутся ещё строки старого сборщика
и строки нового. После завершения миграции проверяется, что:

- исторические основные поля содержат округлённые значения прежних `acc`;
- исторический `book_age_s` равен нулю, остальные сохраняемые поля не изменены;
- уже записанные новые строки не затёрты нулевыми `acc`;
- новые строки принимаются и до, и после завершения миграции;
- состав, типы, значения по умолчанию и кодеки столбцов совпадают с новой базой;
- повтор миграции после новых записей не меняет данные и схему;
- число строк сохраняется.

Контейнер ClickHouse временный, без сети и опубликованных портов; удаляется
вместе с данными при завершении, включая ошибку. Рабочая база не используется.
Вставка выполняется через `clickhouse-client` в формате `JSONEachRow`.
Наличие каждого отправляемого столбца проверяется явно: ClickHouse может
молча пропустить неизвестное поле при `input_format_skip_unknown_fields=1`.

## Локальный запуск

Нужны Python 3.10+, Git и Docker, доступный текущему пользователю:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
git fetch origin main
python tests/test_clickhouse_upgrade.py --base-ref origin/main
```

`--base-ref` задаёт старую версию кода и схемы. Текущая рабочая директория
проверяется вместе с незакоммиченными изменениями. `--target-ref REV` позволяет
проверить другую Git-ревизию, оставив тест из текущей директории.
Образ ClickHouse 25.8 закреплён по digest; другую версию задаёт `--image`.

## Проверить миграцию для интеграции Bybit

Версия до Bybit и изменения смысла глубины:
`04f51c3fd5cfadefb59787840f26dfa312cb3a70`.

```bash
python tests/test_clickhouse_upgrade.py \
  --base-ref 04f51c3fd5cfadefb59787840f26dfa312cb3a70
```

Оба сценария должны пройти. По умолчанию тест вызывает рабочую миграцию
`deploy/migrations/book_depth.py` из проверяемой версии кода, через настоящий
`clickhouse-client`, направленный во временный контейнер. Дополнительные
параметры для успешного запуска не требуются.

Чтобы воспроизвести отсутствие миграции на прежней версии PR:

```bash
python tests/test_clickhouse_upgrade.py \
  --base-ref 04f51c3fd5cfadefb59787840f26dfa312cb3a70 \
  --target-ref acad0fe095dfd20ab447f3f304729dbb8ef0e1ad
```

Этот запуск должен упасть из-за отсутствующего `book_age_s`. Если добавить
только этот столбец через `--extra-sql`, проверка истории всё равно упадёт:
основные поля сохраняют прежнюю сумму вместо `acc`. Параметр
`--migration-script FILE` позволяет проверить другую реализацию миграции.

### Как устроен переход

1. `prepare` добавляет `book_age_s` с историческим значением 0 и сохраняет
   старые столбцы и типы. Старый и новый сборщики могут продолжать запись.
2. Обновляются все сборщики. Завершаются записи и запросы старых процессов.
3. `finish` переносит ненулевые `acc` в основные поля с округлением. Новые
   строки, у которых `acc` по умолчанию равен 0, сохраняют основные значения.
   У старых строк нулевой `acc` означает и нулевую обычную глубину: обычная
   сумма входила в накопленную. После завершения мутации поля переводятся
   в `UInt64`, затем удаляются `acc` и `band_valid`.

Коллекторам новой версии не требуется останавливаться на время переноса
истории. Перезапуск процесса при обновлении кода остаётся обычным действием
деплоя; отсутствие пропущенных биржевых сообщений этим тестом не проверяется.
Тест проверяет последовательность записей двух поколений, а не нагрузку
при конкурентных вставках. На этапе совместимости читатели должны различать
смысл основных полей по `collector_version`; единый смысл появляется после
завершения переноса истории.

`deploy/deploy.sh` вызывает тот же файл: `prepare` после создания таблиц,
`finish` после перезапуска сборщиков и проверки активности systemd units.
Учитываются как включённые, так и уже работающие экземпляры сборщиков.
Флаг `--defer-migration-finish` откладывает завершение до ручной команды.
Порядок первого обновления описан в [инструкции деплоя](../deploy/README.md).

`test_deploy.py` выполняет настоящий `deploy.sh` с подставными SSH, rsync и
systemctl. Он проверяет порядок подготовки, перезапуска, проверки активности
и завершения; ручной режим; остановку при ошибке подготовки, поиска сборщиков,
перезапуска или проверки активности; доставку миграции и примера конфига.
Работающий, но выключенный из автозапуска сборщик тоже должен обновляться.
Удалённые серверы при этом не используются.

## GitHub Actions

Workflow **ClickHouse schema upgrade** запускается только для PR: открытие,
новый push и повторное открытие. Отдельного запуска на `push`, после слияния
и ручного `workflow_dispatch` нет. Используется тест из проверяемого результата
слияния PR с базовой веткой, а не закреплённый тест из `main`.

Workflow сначала запускает тестовые скрипты сборщиков и деплоя, затем
интеграционный тест с рабочей миграцией. Старая схема берётся из базового
коммита PR; секреты не требуются. Для форка GitHub может потребовать
**Approve workflows**.

Повтор старого запуска через **Re-run** проверяет прежнюю версию. Для проверки
изменённого теста или миграции нужен новый push в ветку PR. Для запрета слияния
при ошибке check **schema-upgrade** должен быть обязательным в защите `main`.
